# Recovery Strategies — лабораторная работа №7

## Что реализовано

- Адаптивная лента, плитка, страница «Подробнее», форма добавления и авторизация. Цвета, логика лайков и смены изображения, оптимизированный SQL из исправленной ЛР6 сохранены.
- В плитке 1 колонка при ширине менее 360 px, 2 при 360–767 px, 3 при 768–1099 px, 4 начиная с 1100 px. На широком экране лента/«Подробнее» показывают видео и описание рядом. Максимальная ширина приложения 1200 px.
- Кнопка «Подробнее» открывает отдельную страницу; «К плитке» меняет только состояние интерфейса Redux. Фильтр и результаты остаются неизменными. Выход по-прежнему сбрасывает фильтры. F5 по-прежнему сбрасывает Redux в гостевое состояние, не удаляя cookie.
- Сборка `pages` принудительно использует mock; авторизация и добавление недоступны. Публичный frontend никогда не посылает запросы к API. Пути к изображениям и видео относительные, поэтому работают под любым именем репозитория.
- PWA: manifest, иконки, service worker с версионированным кешем статических ресурсов, включая mock-видео. В автономном режиме поддерживаются byte range запросы видео. Service worker регистрируется только в публичной production-сборке, не кеширует локальный API или сессии.
- Vite (сервер Node.js) выполняет обратное проксирование `/api` и `/s3` по HTTP на FastAPI. Для LAN запускается HTTPS с сертификатом, содержащим IP ноутбука. FastAPI выставляет Secure для cookie HTTPS-запросов; HTTP-режим localhost остаётся рабочим.
- Deployment-диаграмма не включена: по договорённости выполняется отдельно.

## 1. Обычный запуск на ноутбуке (Windows, VS Code)

Сохрани старый архив. Останови работающие frontend и backend. Замени исходники из ZIP, оставив имя корневой папки `recovery_strategies` и прежнюю папку `frontend/node_modules`, если она сохранена. Содержимое `docker-compose.yml` не изменено относительно исправленной ЛР6; подключён существующий внешний том `recovery_db_check_copy`. Не удаляй Docker volumes. Архив не содержит самих данных PostgreSQL и MinIO.

Из корневой папки проекта, в первом терминале:

```powershell
cd backend
docker compose up -d
python -m uvicorn main:app --reload
```

Если Docker уже запущен, `docker compose up -d` можно пропустить. Swagger: http://localhost:8000/docs.

Во втором терминале из корневой папки:

```powershell
cd frontend
npm ci
npm run dev
```

`npm ci` нужен один раз, если папки `node_modules` нет. Node.js 22 подходит. Не нужно устанавливать ничего глобально. Сайт: http://localhost:5173. При проверке убедись, что можно войти под старым пользователем, добавить/заменить медиа, фильтровать и поставить лайк. Кнопка «Подробнее» открывает выбранную стратегию, кнопка «К плитке» сохраняет старые фильтры.

## 2. GitHub Pages и PWA (только mock)

Сначала можно проверить production-сборку локально. Из `frontend`:

```powershell
npm run build:pages
npm run preview:pages
```

Vite выводит адрес, обычно http://127.0.0.1:4173. На localhost service worker разрешён. Открой плитку, примени диапазон, например 10–60 мин, открой «Подробнее», вернись в плитку. Фильтр 10–60 и результаты (синхронная и асинхронная репликация) должны сохраниться. В DevTools → Application проверь Manifest, Service Workers и Cache Storage; после активации worker можно включить Offline и обновить страницу. Preview не связан с бэкендом.

В корне архива есть `.github/workflows/pages.yml`, который собирает только frontend и публикует `frontend/dist`. Для реальной публикации нужен свой репозиторий GitHub и право на Pages. Не публикуй backend, ключи, дампы БД и реальные данные. Вариант с новым публичным репозиторием:

1. Создай на GitHub пустой публичный репозиторий, например `recovery-strategies` (без начального README). Если GitHub требует тариф для приватного репозитория, используй публичный репозиторий только для mock-фронтенда.
2. Помести в локальный клон репозитория папку `frontend` (без `node_modules`, `dist`, `certs`), папку `.github` и корневой `.gitignore`. В GitHub Desktop или Git отправь эти файлы в ветку `main`. Не отправляй исходники backend и приватные файлы. Корень репозитория должен содержать `frontend/package.json` и `.github/workflows/pages.yml`.
3. В репозитории Settings → Pages → Build and deployment → Source → GitHub Actions. Затем Actions → Recovery Strategies — GitHub Pages → Run workflow, выбери `main` → Run workflow. Дождись успешного workflow. Если Pages был выбран до push, сборка стартует автоматически.
4. Settings → Pages покажет фактический URL, например `https://<имя>.github.io/recovery-strategies/`. Открой его на телефоне. Android Chrome: меню → Установить приложение/Добавить на главный экран. iPhone Safari: Поделиться → На экран «Домой» (открывать как веб-приложение, если есть такой переключатель). Открой установленное приложение. Проверь, что используются mock-стратегии. Установка зависит от браузера и ОС.

Если всё уже находится в своём репозитории, не создавай новый без необходимости: структура должна совпадать с путями workflow, а Source — GitHub Actions. Если ветка не main/master, запусти workflow вручную после добавления ветки в `on.push.branches` или настрой его под свою ветку.

Официальные инструкции:
- https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site
- https://v6.vite.dev/guide/static-deploy

## 3. HTTPS и доступ с телефона к бэкенду ноутбука

Используй доверенную локальную сеть, например домашний Wi-Fi. Телефон и ноутбук должны быть в одной сети без изоляции клиентов. Не открывай порт на роутере и не публикуй локальный dev-сервер в Интернет. На ноутбуке оставь FastAPI запущенным на `127.0.0.1:8000`. Для телефона нужен только порт 5173, а не прямой доступ к PostgreSQL, MinIO, Redis или FastAPI.

1. В PowerShell выполни `ipconfig` и найди IPv4 именно адаптера Wi-Fi (не Docker, VPN или VirtualBox). IP может меняться.
2. Установи mkcert, если его ещё нет. В PowerShell: `winget search mkcert`, затем установи найденный пакет mkcert от FiloSottile с его точным ID (обычно `FiloSottile.mkcert`). Официальный источник: https://github.com/FiloSottile/mkcert. После установки открой новый терминал, чтобы обновился PATH.
3. Останови обычный frontend (`Ctrl+C` в его терминале). В папке `frontend` выполни следующую команду, подставив **реальный IPv4 ноутбука вместо 192.168.1.25**:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\create-certificate.ps1 -LanIp 192.168.1.25
```

Скрипт локально создаёт CA mkcert (если ещё не создан) и сертификат с SAN для `localhost`, `127.0.0.1` и IPv4 ноутбука. Результат в `frontend/certs/`: `recovery-cert.pem`, `recovery-key.pem`, `rootCA.crt`. Сертификаты и приватные ключи не включены в архив, не добавляются в git. При изменении IPv4 перегенерируй сертификат командой выше с новым адресом.

4. В этом же терминале запусти HTTPS:

```powershell
npm run dev:lan
```

Vite выведет URL. На ноутбуке открой `https://localhost:5173` и проверь, что вход работает. На телефоне перед авторизацией нужно установить доверие к локальному CA: передай только `frontend/certs/rootCA.crt` на свой телефон. Android: настройки безопасности → установка CA-сертификата (названия зависят от устройства). iOS: установи профиль сертификата, затем Настройки → Основные → Об этом устройстве → Доверие сертификатам → включи полное доверие этому CA. Никогда не передавай `recovery-key.pem` или `rootCA-key.pem`. Установка CA расширяет доверие устройства; делай это только для созданного тобой CA, после защиты можешь удалить его из доверенных на телефоне. Не вводи логин и пароль, если браузер предупреждает о недоверенном сертификате.
5. Если Windows Firewall спрашивает разрешение, разреши Node.js только в частной сети. Если телефон не подключается, проверь совпадение Wi-Fi, IPv4, отсутствие VPN/изоляции и разрешение TCP 5173 на частном профиле брандмауэра. Не отключай брандмауэр целиком.
6. На телефоне открой `https://<реальный IPv4 ноутбука>:5173`. Войди под старым аккаунтом. Покажи ленту, плитку, добавление с backend. В Network запросы идут на тот же HTTPS-адрес `/api`, а медиа — `/s3`; Vite пересылает их на localhost:8000. Логин остаётся через Axios напрямую. GitHub Pages не подключается к ноутбуку.

## 4. Что показывать для 17 скриншотов методички

1. GitHub Pages на телефоне, mock.
2. Установка/иконка PWA на главном экране.
3. Запущенная PWA (лента).
4. Плитка с применённым фильтром 10–60 мин.

6. Возврат к плитке со старым значением фильтра и результатами.

12. Добавление с веб-сервисом.

14. Браузер по HTTPS: информация о защищённом соединении/сертификате.
15. `frontend/src/recovery_strategies_styles.css`: `--columns`, `.strategy-grid` и `repeat(var(--columns), minmax(0, 1fr))`.
16. Тот же CSS: media queries 360, 768, 1100 px, `--columns` и `--card-cover-height`.
17. Тот же CSS: `.feed-card`, `.strategy-video`, `.app-shell`, параметры ширины/высоты и адаптивная раскладка.

## 5. Проверки перед выдачей

Проверены TypeScript (tsc), синтаксис Python/Node, реальные Redux reducers/thunks в mock-режиме, фильтрация 10–60 и сохранение фильтра после возврата, пути к медиа с относительной базой и блокировка HTTP-запросов в Pages. Проверен генератор service worker на тестовом дереве статических файлов. Архив не включает платформенные зависимости. Полная сборка Vite и реальная публикация не были выполнены в среде подготовки: исходный node_modules содержит Windows-бинарники, а доступ к npm registry из среды ограничен. Полную сборку, установку PWA на телефон и HTTPS с реальным IP нужно проверить на ноутбуке/телефоне. Deployment-диаграмма отдельно.
